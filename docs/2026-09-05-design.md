# clipfeed design

Date: 2026-09-05
Status: Proposed. Nothing in this document is a claim until a verdict on a pushed SHA backs it.
Working name: clipfeed. Rename before publication.
Amended: 2026-09-06, alignment with the shared data-platform discipline (DATUM, local brief). Amendments are appended in place under the section they touch and listed at the end; the original text is kept.

## Purpose

A single repository that turns raw gameplay video into training-ready tensors, measures where the pipeline stalls, serves a small vision-language model over the result, and owns the latency and cost numbers. It exists to answer one question a data-platform reader will ask: can this person move from object storage throughput to decode to serving in one week, and show numbers rather than describe them.

The artifact is targeted at the General Intuition Fullstack Engineer, Data Platform role. It is not a compliance repo. Verification discipline is carried over from prior work; the domain code is new.

## Decisions taken

GPU budget is a few rented hours on AWS. Corpus is public OpenAI VPT contractor MP4 shards via the Hugging Face mirror, 50 to 200 GB, with synthetic scaling held behind a gate that opens only if the real corpus proves decode-bound. Serving target is Qwen2-VL-2B under vLLM. Infrastructure is Terraform in one region. Timeline is three days plus a short day 0. Both lanes are attempted; the second lane carries a wall-clock kill switch.

## Shape

Five containers, one driver, one ledger.

fetch pulls shards from the mirror into S3, then S3 to the local data volume. It is the network I/O stage and emits bytes per second and per-object latency.

decode reads MP4 at the native 20 Hz and samples to 5 Hz with PyAV. It emits frames per second, CPU utilisation, and read-wait time. The I/O-bound versus decode-bound classification is made here by comparing read wait to decode time.

pack resizes, normalises, and writes fixed-shape tensor shards. It emits write throughput and bytes on disk.

serve runs vLLM with Qwen2-VL-2B over packed frames and sweeps batch size against quantisation (fp16, int4) with prefix-cache hit rate as a measured cell rather than an on/off axis. It emits p50 and p95 latency, tokens per second, GPU utilisation, and cost per thousand requests computed from the on-demand price recorded at run time.

driver chains the stages by S3 prefix and calls the gates. gates holds deterministic checks over verdict JSON, each with a twin fixture that must fail. infra holds Terraform for the VM lane and the EKS lane. STATUS.md is generated from verdicts by build-status.mjs and is never hand-written.

Amended 2026-09-06. "A twin fixture that must fail" is too weak: the twin must fail for exactly the planted reason, and the checker compares the twin row's violations against its planted expectation key for key. gates also holds the ledger checker, and the checker ships with its own positive and negative controls (fixture rows that must pass and fixture rows that must each fail for a named reason), run in CI before anything is built. The status builder is Python, scripts/build_status.py, so CI needs one toolchain; it has a --check mode that re-renders and fails the build if the committed STATUS.md differs.

Every stage reads a manifest, writes a manifest, and never touches another stage's files. That boundary is the Kubernetes contract, present from the first local run.

## Verdict schema

One verdict per stage per run, appended to runs/<run_id>/verdicts.jsonl and committed to the repository.

    run_id, stage, git_sha, instance_type, region, price_per_hour_used,
    dataset_revision, dataset_licence,
    input_manifest_sha, output_manifest_sha,
    wall_s, bytes_in, bytes_out, items,
    metrics (stage specific),
    gate: PASS | FAIL | UNEVALUABLE:<reason>

Floors and tolerances live in gates/floors.json keyed by instance type. A run on an instance type with no floor is UNEVALUABLE, not FAIL.

Amended 2026-09-06. The schema above cannot express a twin, so it is replaced by the row shape the sibling repos share. One JSON file per stage per cell, not a jsonl, because a per-file hash is what the source binding pins.

    kind                GATE_VERDICT
    stage               fetch | decode | pack | serve | lane-parity | teardown | cost-backfill
    lane                1 (VM) | 2 (EKS)
    cell                live | twin
    result              GREEN | RED | UNEVALUABLE
    reason              required when UNEVALUABLE
    checks              { check_name: violation_count }
    evaluated           { check_name: items_evaluated }
    planted             twin only: { mutation, mutated_rows, expected_violations: {...} }
    scope               what subset, in words
    params              instance_type, region, price_per_hour_used, dataset_revision,
                        dataset_licence, floors applied
    metrics             stage specific, plus input_manifest_sha, output_manifest_sha,
                        wall_s, bytes_in, bytes_out, items
    run_id
    traverse_sha        commit of the emitter
    traverse_worktree   clean | dirty; a dirty row fails the checker
    content_hash        sha256 of the stage's output manifest
    content_hash_basis  what bytes, what canonical order
    ran_at              UTC
    runner              local | github-actions | <instance_type>

Rows that CI can regenerate (the synthetic-clip lane) are build output under gates/out/ and are not committed. Rows from runs that cannot be regenerated (anything on a rented instance) are committed under runs/<run_id>/verdicts/ with a runs/<run_id>/SOURCE.md that binds every file to its sha256 over LF-normalised bytes and records the replay command; the checker recomputes every hash and fails on any unbound, missing, or altered file. The hand-copy seam is otherwise unverified and is said to be.

Every floor in gates/floors.json carries a source string saying where the number came from. A floor set from the first run's own numbers makes that run's PASS circular; such a floor is labelled descriptive and the gate over it is reported as a baseline, not a claim, until a prior figure with a citation replaces it.

## Gates

fetch-throughput: sustained S3 to disk throughput above the floor for the instance type. Twin: a tc-throttled run.

decode-bottleneck: classifies the run I/O-bound if read wait exceeds half of stage wall time, else decode-bound. This is a classification, not a pass. Twin: a cgroup io.max run that must classify I/O-bound. The synthetic-scaling lane opens only on decode-bound.

pack-shape: every shard matches declared dtype and shape; frame count equals decode output. Records the container image digest. Twin: one truncated shard.

serve-sweep-complete: the full matrix ran. Any missing cell is UNEVALUABLE, not a partial pass. Twin: a matrix with a hole.

serve-regression: the batch-1 configuration must be worse on cost per thousand than the best batched configuration by the declared margin. Twin: a fixture with equal numbers.

lane-parity: EKS numbers within declared tolerance of the VM lane for the same cells. Twin: a fixture thirty percent off. Explicit outcome UNEVALUABLE:quota-not-granted.

teardown: after destroy, an inventory script lists every resource by repo tag across EC2, EBS, EKS, ELB, ECR, S3, IAM and Cost Explorer, and passes only on an empty result. Terraform state is an index, not a decision. UNEVALUABLE until all run verdicts are on a pushed SHA.

cost-backfill: actual billed cost from Cost Explorer, UNEVALUABLE until the data lands, then a dated row.

A gate that has never gone red is not a gate. Twins are written before the stage they test passes.

Amended 2026-09-06. Two kinds of twin, and both are rows. A fixture twin plants one defect into a copy of the metrics or a shard (a misclassified bottleneck, a truncated shard, a throttled throughput figure, a matrix with a hole) and runs in CI on every push. A runtime twin (the tc-throttled fetch, the cgroup io.max decode) needs the rented instance and Linux, runs once per lane, and is committed under runs/ like any unrepeatable row. A stage is CLAIMABLE only when its live cell is GREEN and every twin cell is RED for exactly the planted reason. A twin that comes back GREEN, or RED for a different reason, is a broken gate: the checker refuses to derive status at all rather than render a wrong table. A twin over a live cell that was UNEVALUABLE is UNEVALUABLE with the same reason; a gate that could not evaluate cannot be shown red.

Lane status vocabulary, derived and never typed: CLAIMABLE, PARTIAL (live GREEN, twin missing or unevaluable), UNCLAIMED (no live row, or live RED), UNEVALUABLE (live unevaluable). Any of these strings found inside a row fails the checker.

## Infrastructure

Tagging is the spine. Every resource carries repo, run_id, and lane. The teardown inventory queries by these tags only.

VM lane: one g5.xlarge in us-east-1 from a pinned Deep Learning AMI with the driver preinstalled. gp3 root plus a separate gp3 data volume with IOPS and throughput set in variables. S3 bucket inside the module with force_destroy and a seven-day lifecycle rule. Instance role scoped to the bucket prefix. SSM Session Manager, no SSH ingress. No static credentials anywhere.

EKS lane: cluster, one managed GPU node group (g5.xlarge, min 0, max 1), one small CPU node group. NVIDIA device plugin as the EKS add-on. Stages as Jobs with ttlSecondsAfterFinished, chained by S3 prefix. Serving as a Deployment with an HPA on GPU utilisation from the DCGM exporter. Images in ECR pinned by digest in manifests.

Teardown for both lanes: push verdicts, destroy, inventory, commit the teardown verdict. A second inventory pass on day 3 catches stragglers.

## Schedule

Day 0: g5 quota request for the VM and the node group. ECR repositories. Mirror gating and licence check. Repo skeleton, twins directory, floors file.

Day 1, VM lane complete: local pipeline on 20 to 50 GB with gates one to three and their twins in the morning. VM apply, region-local pull of 100 to 200 GB, pipeline rerun and bottleneck classification in the afternoon. vLLM sweep, gates four and five, push, destroy, inventory in the evening. GPU off before sleep. Halt-gate for the EKS lane: lane one green and quota granted.

Day 2, EKS lane: cluster apply, node group, add-on, images by digest in the morning. Jobs, Deployment, HPA, sweep rerun, lane-parity in the afternoon. Push, destroy, inventory in the evening. Kill switch at 22:00 regardless of state: destroy, record the blocker, ship manifests as UNCLAIMED.

Day 3, evidence and writing: fresh-clone reproduction of the day 1 verdicts on CPU. Report, STATUS.md from verdicts, cost backfill if landed, second inventory pass.

## Claim ceiling

After day 3 the repository may claim: pipeline throughput and I/O classification on one instance type and one disk configuration; serving latency and cost per thousand requests for one model on one GPU across the sweep matrix; API-verified teardown of every provisioned resource. The EKS row is claimable only if lane-parity passed before the kill switch. Nothing about multi-region, nothing about scale beyond the measured corpus, nothing about training.

## Risks

Quota latency and vLLM image pull time are the two items most likely to consume day 2. Both are outside the author's control, which is why the kill switch is a wall-clock time and not a condition. Prefix caching on a VLM will likely show near-zero hit rate; the table reports that rather than omitting the axis. The dataset licence must be confirmed on day 0 and recorded in the fetch verdict.
